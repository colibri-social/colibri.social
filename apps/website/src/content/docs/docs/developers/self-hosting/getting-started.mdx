This guide covers running your own Colibri **AppView**. Deploying the colibri.social website is covered only as far as [connecting a client](#connecting-a-client) needs it.

The AppView lives in [colibri-social/api](https://github.com/colibri-social/api). To work on its code, read [AppView development](/docs/developers/development/appview).

Colibri stores the data of a Space in [ATproto spaces](/docs/developers/architecture/spaces), which puts two requirements on an instance:

1. **Your AppView must be reachable from the PDS of every Space it manages.** Apart from the public profile space, the spaces of a Space name your AppView in a `managing-app` policy, so the PDS calls your AppView before it issues a credential. While your AppView is unreachable, its Spaces are unreadable. See [Sync](/docs/developers/architecture/sync).
2. **A Space lives on the AppView that manages it.** Everyone in a Space uses that instance, because an AppView holding no credential for gated data cannot index it.

## What you'll run

- The **AppView**, which serves the XRPC API, the WebSocket endpoints and the voice SFU in one process.
- A **PDS running the spaces alpha**, which hosts the account of every Space your instance creates.

Alternatively, you'll soon be able to use a PDS from a hosted service. We'll update this page with more information.

Storage defaults to libSQL in a file on the `appview-data` volume. Postgres is available as an overlay.

## Prerequisites

- **A PDS you control** running the spaces alpha (`ghcr.io/bluesky-social/atproto:pds-spaces-alpha`), plus its admin password. See [Which PDS needs the spaces alpha](#which-pds-needs-the-spaces-alpha).
- **A domain with TLS**, for example `appview.example.com`. The AppView identifies itself with a `did:web` derived from a hostname and serves its DID document at `/.well-known/did.json`. It refuses to boot on a `did:web` made from a bare IP address.
- **Wildcard DNS for Space handles.** Spaces get handles under `COMMUNITY_HANDLE_DOMAIN`, answered by the PDS, so `*.${COMMUNITY_HANDLE_DOMAIN}` must resolve to the PDS under a covering certificate.
- **Docker** and **Docker Compose** on a Linux `amd64` server. The published image is built for `linux/amd64`.

## Which PDS needs the spaces alpha

- **The PDS at `PDS_URL`** must run the spaces alpha. Every Space created with `social.colibri.beta.community.create` is an account on it, and the AppView creates that account's spaces there.
- **The PDS of an account you bring yourself** must implement the `com.atproto.space` policy methods. `social.colibri.beta.community.authorizeHost` and `social.colibri.beta.community.adopt` put a Space on an existing account and fail with `SpacesUnsupported` on a PDS without them.
- **A member's own PDS** can be a stock PDS. The AppView hosts the space repos of members whose PDS has no spaces support, and stores their uploads in the bucket set with `POLYFILL_S3_*`.

[Hosting](/docs/developers/architecture/hosting) explains how the AppView hosts member repos and how a Space runs on an account you bring yourself.

## Run it

<Steps>

1. Clone the repository and create your configuration:

   ```sh
   git clone https://github.com/colibri-social/api.git
   cd api
   cp .env.example .env
   ```

2. Fill in `.env`. The AppView refuses to boot without `APPVIEW_DID`, `PUBLIC_URL`, `SIGNING_KEY`, `CREDENTIAL_ENCRYPTION_KEY`, `PDS_URL` and `COMMUNITY_HANDLE_DOMAIN`. The file carries the `openssl` commands that generate the two secrets. Set `PDS_ADMIN_PASSWORD` too, so the AppView can create Spaces.

3. Start it:

   ```sh
   docker compose up -d
   ```

   Compose pulls `ghcr.io/colibri-social/api:stable` and runs the AppView on libSQL against the `appview-data` volume.

4. Route your domain to port `3000` of the `appview` container through a TLS-terminating reverse proxy. `docker-compose.yml` publishes the SFU media ports only, so run the proxy on the same Docker network or add a port mapping in a `docker-compose.override.yml`.

5. Confirm the AppView is healthy:

   ```sh
   curl https://appview.example.com/health
   ```

6. Confirm the DID document resolves and lists `#colibri_appview`:

   ```sh
   curl https://appview.example.com/.well-known/did.json
   ```

7. Confirm the AppView identifies itself:

   ```sh
   curl https://appview.example.com/xrpc/social.colibri.beta.server.describeServer
   ```

</Steps>

The AppView registers `PUBLIC_URL` as its notification endpoint when it calls `com.atproto.space.authorizeSpaceSync`. The PDS calls `com.atproto.space.confirmRegistration` and `com.atproto.space.notifySpaceUpdate` on it, and only accepts an HTTPS URL on a public address. When the PDS cannot reach it, write notifications never arrive and every Space on your instance falls back to the sweep interval, `SYNC_SWEEP_SECONDS`.

## The image

The [Image workflow](https://github.com/colibri-social/api/blob/main/.github/workflows/image.yml) publishes `ghcr.io/colibri-social/api` for `linux/amd64` on every push to `main`.

| Tag | Published |
| --- | --- |
| `edge` | On every push to `main` |
| `sha-<commit>` | On every push to `main`, named after the first seven characters of the commit |
| `<version>` | When the version in `apps/appview/package.json` changes |
| `stable` | Together with each `<version>` tag |

`docker-compose.yml` runs `stable`. Set `IMAGE` in `.env` to run another tag:

```ini title=".env"
IMAGE=ghcr.io/colibri-social/api:edge
```

To build the image from your checkout, run `docker compose up -d --build`.

The image also contains `colibri-admin`, the command line for the database and for a cluster of AppView nodes. Run `docker compose exec appview colibri-admin --help` to list its commands.

## Compose files and profiles

`docker-compose.yml` is the base. It defines the `appview` service and two optional profiles:

| Profile | What it adds |
| --- | --- |
| `updater` | A container that pulls the AppView image on an interval and restarts the AppView when a newer image arrived |
| `blobs` | A [SeaweedFS](https://github.com/seaweedfs/seaweedfs) server that provides the S3 bucket for `POLYFILL_S3_*` |

Three overlay files compose on top of the base:

| Overlay | What it adds |
| --- | --- |
| `docker-compose.postgres.yml` | Postgres, and a `DATABASE_URL` that points at it |
| `docker-compose.pds.yml` | A local spaces-alpha PDS and a private PLC directory, for development |
| `docker-compose.integration.yml` | The same pair, ephemeral, for the integration suite |

```sh
docker compose -f docker-compose.yml -f docker-compose.postgres.yml up -d
```

`docker-compose.scaled.yml` is a separate stack for a cluster. See [Running a cluster](#running-a-cluster).

### Automatic updates

The `updater` profile keeps a single AppView current:

```sh
docker compose --profile updater up -d
```

The updater pulls the image named by `IMAGE` every six hours and restarts the AppView when the pulled image differs from the running one. Set `UPDATE_INTERVAL_SECONDS` in `.env` to change the interval. An AppView with no other node to send clients to drains for 15 seconds before it stops.

### File storage for members on a stock PDS

The `blobs` profile runs the bucket that holds uploads from members whose PDS cannot host space files. Set the profile, a bucket name and both keys in `.env`, and leave `POLYFILL_S3_ENDPOINT` unset:

```ini title=".env"
COMPOSE_PROFILES=blobs
POLYFILL_S3_BUCKET=colibri-blobs
POLYFILL_S3_ACCESS_KEY_ID=<access key>
POLYFILL_S3_SECRET_ACCESS_KEY=<secret key>
```

The compose files point the endpoint at the SeaweedFS container, which creates the bucket on the first upload. Any S3-compatible bucket works in its place: set `POLYFILL_S3_ENDPOINT` to it and leave the profile out. With no bucket configured, uploads from those members fail with `BlobStorageUnavailable`.

### Moving from libSQL to Postgres

`colibri-admin db copy` copies every table from a libSQL database into Postgres and checks the row counts. Stop the AppView while it runs. The libSQL database has to be on the current migrations, so let the AppView start once on libSQL after an update before you copy.

Set `POSTGRES_PASSWORD` and `POSTGRES_REPLICATION_PASSWORD` in `.env` first. `docker-compose.scaled.yml` refuses to start without them.

<Steps>

1. Stop the AppView and start Postgres:

   ```sh
   docker compose stop appview
   docker compose -f docker-compose.scaled.yml up -d postgres
   ```

2. Copy the data:

   ```sh
   docker compose -f docker-compose.scaled.yml run --rm --no-deps appview \
     colibri-admin db copy --from file:/data/colibri.db \
     --to "postgres://colibri:$POSTGRES_PASSWORD@postgres:5432/colibri"
   ```

   The copy creates the Postgres tables and refuses a target that already has rows. Pass `--truncate` to empty the target first.

3. Start the AppView on Postgres:

   ```sh
   docker compose -f docker-compose.scaled.yml up -d
   ```

</Steps>

The libSQL file stays in the data volume. Starting `docker-compose.yml` again runs the AppView on it.

## Voice

Voice runs on a [mediasoup](https://mediasoup.org) SFU inside the AppView process. WebRTC media flows directly between clients and the host, outside your reverse proxy.

- **Announced IP.** Set `SFU_ANNOUNCED_IP` to the public IP of the host. It is required behind NAT, which covers most cloud hosts.
- **Media ports.** Each SFU worker listens on one port for both UDP and TCP, counting up from `SFU_RTC_PORT` (default `40000`). `SFU_WORKER_COUNT` defaults to the number of CPUs. Open `SFU_RTC_PORT` through `SFU_RTC_PORT + SFU_WORKER_COUNT - 1` for UDP and TCP. The compose files publish `40000` through `40031`.
- **TURN for restrictive networks.** `SFU_ICE_SERVERS` takes a JSON array of [`RTCIceServer`](https://developer.mozilla.org/en-US/docs/Web/API/RTCIceServer) objects that clients receive. With `TURN_KEY_ID` and `TURN_KEY_API_TOKEN` set, every transport also gets its own Cloudflare TURN credentials, valid for 24 hours.

Set `VOICE_ENABLED=false` to run an AppView without voice.

## Connecting a client

The client reads its AppView at build time from `VITE_COLIBRI_APPVIEW_URL`. A build with the variable unset uses `https://api.colibri.social`. **We are actively working to improve this.**

The client derives the AppView's DID from the host of that URL, as `did:web:<host>`. The host must therefore be the one in your `APPVIEW_DID`.

<Steps>

1. Clone the client repository and install its dependencies:

   ```sh
   git clone https://github.com/colibri-social/colibri.social.git
   cd colibri.social
   pnpm install
   ```

2. Build the workspace with your AppView URL:

   ```sh
   VITE_COLIBRI_APPVIEW_URL=https://appview.example.com pnpm build
   ```

   `packages/app/.env.example` lists the variables the client build reads. A `packages/app/.env` file works in place of the inline variable.

3. Deploy the website from `apps/website`. It serves the client at `/app`, and it serves the OAuth client metadata for your AppView at `/c/<appview host>/oauth-client-metadata.json`, with scopes pinned to `did:web:<appview host>`. The `client_id` in that document starts with the `SITE` origin from `apps/website/src/site.ts`, so set `SITE` to the origin you deploy to.

4. Allow the client's origin on the AppView:

   ```ini title=".env"
   CORS_ORIGINS=https://chat.example.com
   ```

</Steps>

The native shell bundles the same build. [Testing native builds](/docs/developers/development/native) covers building it.

## Telemetry

Once a day, the main node sends an anonymous heartbeat to `COLIBRI_TELEMETRY_URL`. It holds a random instance ID, the version, flavor and roles, the database and Node.js major versions, the operating system, whether voice is set up, and four counts: nodes, Spaces, users seen in the last 30 days, and voice minutes in the last day. Each count is rounded to `0`, `1-10`, `11-100`, `101-1k`, `1k-10k` or `10k+`.

The first start logs a notice, and the first heartbeat goes out an hour later. Set `COLIBRI_TELEMETRY_DISABLED=1` or `DO_NOT_TRACK=1` to turn it off.

## Running a cluster

`docker-compose.scaled.yml` runs the AppView as the main node of a cluster. A cluster has one main node holding the Postgres primary and any number of sub, failover and voice nodes, which share a Tailscale tailnet. The file defines:

| Service | Profile | What it is |
| --- | --- | --- |
| `postgres` | | `ghcr.io/colibri-social/postgres:18`, the official Postgres image with pgBackRest added |
| `appview` | | The AppView with the roles in `ROLES`, on Postgres |
| `seaweedfs` | `blobs` | The S3 bucket for `POLYFILL_S3_*` |
| `caddy` | `caddy` | A reverse proxy on ports 80 and 443 for `PUBLIC_HOST` |
| `alloy` | `monitoring` | Grafana Alloy, which ships metrics and container logs |
| `replica`, `sub`, `voice` | `local-cluster` | A Postgres replica, a sub node and a voice node on one machine, for trying a cluster locally |

The `deploy/` directory holds what the stack and the main node use:

| Directory | Contents |
| --- | --- |
| `deploy/ansible` | The playbooks the main node runs over SSH to provision other nodes. They ship inside the image. |
| `deploy/caddy` | The Caddyfile for the `caddy` profile |
| `deploy/traefik` | `compose.traefik.yml`, which routes the AppView through an existing Traefik in place of Caddy |
| `deploy/postgres` | The Postgres image, the primary's init script, and `backup.sh` |
| `deploy/observability` | Configuration for Alloy, Prometheus, Loki and Grafana |
| `deploy/uptime-kuma` | The logo and styles of the status page |
| `deploy/seaweedfs` | The entrypoint of the `blobs` profile |
| `deploy/updater` | The script behind the `updater` profile |

A node takes one or more of five roles in `ROLES`:

| Role | What the node does |
| --- | --- |
| `main` | Tries for the lock on the Postgres primary. The node holding it takes writes and provisions and updates the other nodes. |
| `failover` | Takes the main role when no `main` node answers, and promotes its own Postgres when the primary stays unreachable |
| `api` | Serves XRPC requests |
| `live` | Serves the event socket |
| `voice` | Runs the voice SFU |

Start the main node with Caddy in front:

```sh
docker compose -f docker-compose.scaled.yml --profile caddy up -d
```

`colibri-admin` manages the cluster from inside the main node's AppView container. `colibri-admin node add` provisions a server, `colibri-admin node shutdown` drains one, `colibri-admin rollout now` starts a rolling update, and `colibri-admin db status` reports which Postgres is the primary. Commands that interrupt clients or delete data are marked in `colibri-admin --help` and ask for confirmation.

[Running a Cluster](/docs/developers/self-hosting/cluster) is the operator guide: setting up the main node, adding and retiring nodes, rolling updates, the main role, Cloudflare, database failover, backups, monitoring and the status page.

## Configuration

The AppView reads its configuration from environment variables, parsed in `apps/appview/src/config.ts`. Compose passes `.env` into the container. An invalid value stops the AppView at boot with a message naming the variable.

### Required

| Variable | Purpose |
| --- | --- |
| `APPVIEW_DID` | The `did:web` this instance answers as, for example `did:web:appview.example.com`. The host must be a name. |
| `PUBLIC_URL` | Where this AppView is reachable from the public internet |
| `SIGNING_KEY` | A secp256k1 private key as 64 hex characters. Its public half is published in the DID document. |
| `CREDENTIAL_ENCRYPTION_KEY` | 32 bytes in base64. Encrypts the passwords and OAuth sessions of Space accounts at rest. |
| `PDS_URL` | The spaces-alpha PDS where Spaces are created |
| `COMMUNITY_HANDLE_DOMAIN` | The domain Space handles live under. `*.` of it must resolve to the PDS. |

### Server

| Variable | Default | Purpose |
| --- | --- | --- |
| `NODE_ENV` | `development` | `development`, `production` or `test`. The image sets `production`. |
| `HOST` | `0.0.0.0` | The address the HTTP server binds |
| `PORT` | `3000` | The port the HTTP server listens on |
| `LOG_LEVEL` | `info` | `fatal`, `error`, `warn`, `info`, `debug` or `trace` |
| `CORS_ORIGINS` | unset | Browser origins allowed to call `/xrpc`, comma-separated, or `*` for any. Unset, development allows `http://localhost:4321` and `http://127.0.0.1:4321`, and production allows none. |
| `SERVICE_AUTH_MAX_LIFETIME_SECONDS` | `300` | Rejects service auth tokens that expire further in the future than this |
| `APPVIEW_FLAVOR` | `vanilla` | The flavor `describeServer` reports for this build |
| `DEFAULT_COMMUNITY_DID` | unset | The DID of a Space that `describeServer` reports as `defaultCommunity`. Clients join it after a user creates their profile for the first time. |

### Database

| Variable | Default | Purpose |
| --- | --- | --- |
| `DATABASE_URL` | `file:./data/colibri.db` | A libSQL URL, or a `postgres://` URL to use Postgres. In a cluster it lists every Postgres host that can be the primary. |
| `DATABASE_AUTH_TOKEN` | unset | The auth token for a remote libSQL database |
| `DATABASE_MAX_CONNECTIONS` | `20` | The size of the Postgres connection pool |
| `DATABASE_READ_URL` | unset | A Postgres read replica. Reads go there, and writes and transactions go to `DATABASE_URL`. |

### PDS and Space accounts

| Variable | Default | Purpose |
| --- | --- | --- |
| `PDS_ADMIN_PASSWORD` | unset | The admin password of the PDS at `PDS_URL`. Without it the AppView serves reads and cannot create a Space or repair one whose password stopped working. |
| `PDS_REQUIRES_INVITE` | `false` | Set to `true` when the PDS requires an invite code to create an account |
| `COMMUNITY_EMAIL_DOMAIN` | unset | The domain of the email addresses given to Space accounts |
| `HOST_OAUTH_PRIVATE_KEY` | unset | An ES256 private key in PKCS#8 PEM or JWK form. It turns on the host sign-in behind `community.authorizeHost`. Newlines may be written as `\n`. |
| `HOST_OAUTH_KEY_ID` | `host-oauth-1` | The key ID published with that key |
| `HOST_OAUTH_RETURN_URL` | unset | Where the browser lands after a host sign-in, for example `https://chat.example.com/app` |

### Network and sync

| Variable | Default | Purpose |
| --- | --- | --- |
| `PLC_URL` | `https://plc.directory` | The PLC directory used to resolve `did:plc` identities |
| `JETSTREAM_URL` | `wss://jetstream.us-west.bsky.network` | A Jetstream v2 host |

### Files

| --- | --- | --- |

:::danger[What to back up]
`CREDENTIAL_ENCRYPTION_KEY` decrypts the password of every Space account you hold. After losing it, every Space needs its password reset through the PDS admin API.

If you run the PDS yourself, its PLC rotation key can update the DID document of every Space on it. Losing that key is unrecoverable.
:::
