This section is the practical counterpart to the [architecture pages](/docs/architecture/appview): how to get Colibri running on your own machine and what to expect once it is. If you want to run an instance for other people rather than hack on one, read [Self-Hosting](/docs/self-hosting/getting-started) instead.

## What you're going to run

Colibri is split across two repositories, and local development normally involves both:

| Repository | Contains | Runs as |
| --- | --- | --- |
| [colibri-social/api](https://github.com/colibri-social/api) | The AppView, a Node 24 and TypeScript pnpm workspace, and the compose files for its dependencies | `pnpm dev` on `127.0.0.1:3000` |
| [colibri-social/colibri.social](https://github.com/colibri-social/colibri.social) | The client, its component library, the website that hosts it, the native shell, and this documentation | `pnpm dev:app` on `127.0.0.1:5173` |

The AppView needs no service running alongside it by default: it stores its
data in a libSQL file and syncs member repos directly from their PDS rather
than reading a firehose. Two pieces are optional on top of that:

- **Postgres**, if you'd rather develop against the same dialect a
  production deployment is more likely to run. An overlay swaps the driver,
  see [AppView development](/docs/development/appview#storage).
- **A PDS**, which hosts the repository of every community and member you
  create, plus a small private PLC directory so the DIDs it mints stay
  local. Both come from an overlay in the AppView repository, see
  [Running a PDS](/docs/development/pds).

Your own account is *not* part of the local stack. You log in with a real Atmosphere account on a real PDS (`bsky.social` or wherever your account lives), and only community and message data live on the PDS you configure.

## Prerequisites

- **Node.js `>=24.13.0`** (`.node-version` pins `24.13.1`) and **pnpm `10.33.3`**: run `corepack enable` and the right pnpm is used for you.
- **Docker** and **Docker Compose**, for Postgres and the local PDS overlays.
- An **Atmosphere account**.

## The short path

<Steps>

1. Start the AppView:

   ```sh
   git clone https://github.com/colibri-social/api.git
   cd appview
   pnpm install
   cp .env.example .env
   # fill in .env, then, with a local PDS:
   docker compose -f docker-compose.yml -f docker-compose.pds.yml up -d
   ```

   The AppView refuses to boot without `APPVIEW_DID`, `PUBLIC_URL`,
   `SIGNING_KEY`, `CREDENTIAL_ENCRYPTION_KEY`, `PDS_URL` and
   `COMMUNITY_HANDLE_DOMAIN` filled in. See [AppView development](/docs/development/appview) for what each does.

2. In a second checkout, start the client:

   ```sh
   git clone https://github.com/colibri-social/colibri.social.git
   cd colibri.social
   pnpm install
   cp .env.example .env
   VITE_COLIBRI_APPVIEW_URL=http://127.0.0.1:3000 pnpm dev:app
   ```

3. Open **`http://127.0.0.1:5173`** (not `localhost`, see [below](#dev-mode-is-not-production)) and log in with your Atmosphere account.

</Steps>

That gives you a working client against a local AppView, communities
included. [Running a PDS](/docs/development/pds) explains how the local PDS
overlay works and where its limits are.

## Dev mode is not production

Two things differ when the client runs on a loopback address:

- **The AppView comes from the environment.** `VITE_COLIBRI_APPVIEW_URL` sets the AppView the client talks to. Without it, the client uses the production AppView.
- **The OAuth client is a localhost client.** Per the [AT Protocol localhost client rules](https://atproto.com/specs/oauth#localhost-client-development), the client id is `http://localhost?...` with a `redirect_uri` of `http://127.0.0.1:<port>/app/login`. That redirect URI is why you must browse to `127.0.0.1`, not `localhost`.
